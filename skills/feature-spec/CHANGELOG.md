## v1.0.0 — 2026-08-31（基线）

**创建**：feature-spec skill，需求共识 → 结构化功能清单的工具。

- 定位：grill-me/grilling 拷问（共识不落盘）与 system-audit 审查（需要规划基线）之间的桥梁——拷问共识重建为可验收的功能清单，落盘项目内 `docs/feature-spec.md`
- 输入三来源：grilling 会话共识（默认）/ 直接输入 / 现有项目文档整理
- 模板 `templates/feature-spec.md`：系统定位声明（类型/前台后台/运行硬件/排除项）→ 功能模块总览（P0/P1/P2）→ 模块详情（每功能：描述/前置/输出/实现效果/测试方法/正常结果/优先级）→ 未定事项与风险 → 变更记录
- 纪律：不确认不落盘；不编造验收标准（写不出标「未定」）；功能取舍是用户决策，清单只整理
- 下游：system-audit v1.1 起读 feature-spec 做完成度对照（实现 + 验收达标双重判定）

## v1.2.0 — 2026-09-01（拆工单环节）

**新增**：整合 Matt Pocock to-tickets 的工单拆解能力，不新增 skill 文件，融合进 feature-spec 流程。

- 定位：feature-spec 落盘后「怎么开工」是断的。新增环节 6「拆工单」：把功能清单拆成带验收标准、带阻塞依赖的工单，落盘 `docs/tickets/`
- 工单与清单的关系：清单 = 功能级验收（测试方法+正常结果），工单 = 切片级验收（可追溯、可判定），工单是清单的下一层粒度
- 工单用途：给 agent 当执行计划（开发完可对照验收），给外包技术方当任务书（验收标准防扯皮）
- 吸收 Matt 精华：垂直切片规则（每工单 = 可独立验收的完整切片）、阻塞依赖（无阻塞的立刻开工）、不写具体文件路径/代码片段
- 保留红线：不确认不落盘、不编造验收标准、工单验收标准必须追溯功能清单
- 配套：project-flow v1.2.0 路由表加「要动工 → 拆工单」路径
