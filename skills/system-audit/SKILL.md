# System Audit · 系统审查

对一个软件系统做结构化体检：**14 类审查项**逐项评估打分，加上**规划功能 vs 实际功能**的完成度对照，输出一份带双分数的体检报告并存档，多次评估形成该系统的成熟度曲线。

## 与 feature-spec 的关系（v1.1 起）

功能清单（feature-spec）是审查的**前置规划基线**，审查前先检查（流程第 0 步）：

```
grill-me（拷问需求）→ feature-spec（生成 docs/feature-spec.md）→ system-audit（本技能，读 spec 审查）
```

- 有 feature-spec：系统类型/硬件声明直接读取（不猜 ➖ 项），完成度做「实现 + 验收达标」双重判定
- 没有 feature-spec：提示先走 feature-spec 生成，或完成度标「无法评估」

## 版本选择（第一步就定）

| 版本 | 文件 | 用途 |
|---|---|---|
| `full` | `templates/full.md` | 全量体检（约 76 项 + 功能对照），新项目第一次体检、重大重构前后、深度体检 |
| `core` | `templates/core.md` | 核心快速自查（约 18 项），任何项目 10 分钟出结果 |
| `pre-launch` | `templates/pre-launch.md` | 上线前核查，❌ 必须清零才能上 |
| `operation` | `templates/operation.md` | 运营期体检（建议每季度），重点监控/备份/容量/合规 |
| `outsource-acceptance` | `templates/outsource-acceptance.md` | 外包交付验收，重点交付物/文档/知识产权/超范围开发 |

选版规则：拿不准选 `core`；新项目建档选 `full`；准备上线选 `pre-launch`；已上线选 `operation`；外包交付选 `outsource-acceptance`。

## 评估流程（严格执行）

0. **规划基线检查**（先做）：查项目 `docs/feature-spec.md`（或项目 CLAUDE.md 指定的 spec 位置）。
   - 有 → 读取作为规划基线，系统类型/硬件声明从 spec「1. 系统定位声明」读取
   - 无 → 给用户两条路：a. 先调 feature-spec 生成功能清单（可先 grill-me 拷问）再审查；b. 直接审查，但功能完成度标「无法评估」，报告显著提示「项目缺规划基线，建议先用 feature-spec 生成功能清单」
1. **定系统与版本**：用户说「审查 XX」→ 确认系统名（存哪、什么项目）+ 当前阶段 → 选模板。系统名用 `<目录名或项目名>` 小写短横线形式作为档案名。
2. **系统类型声明**：优先从 feature-spec「系统定位声明」读取；无 spec 时按模板表头确认（Web 应用 / 小程序 / 桌面端 / 服务端 API / 混合），类型不适用的项标记 ➖ 并写「不适用：系统类型为 X」。
3. **功能完成度对照**（所有版本必做）：
   - 基线：feature-spec 的功能清单（首选）；无 spec 时从需求文档/README/CLAUDE.md 提取；**无规划基线时如实标记「完成度无法评估」**，禁止编造
   - 对照代码/页面/接口确认每个功能的实现状态
   - **验收标准核对（有 spec 时）**：按 spec 的「测试方法 + 正常结果」逐功能核对——实现了但验收标准不满足 → 标 🟡 而非 ✅（双重判定）
   - 算完成度（公式见下），输出功能对照表
4. **逐项审查自查**：读代码、查配置、跑只读命令（`ls`/`grep`/`git log`/读 `.env.example` 等），**每一项必须收集证据**。
5. **待确认清单**：自查查不到的事实（如「有无定期备份策略」「服务器由谁运维」）汇总成清单，最后用**是/否/不知道**的简单问答问用户，不问开放题。
6. **填表**：状态 + 证据 + 备注三列全填。拿不出证据的项标 ⚠️ 并在证据列写「未找到」。
7. **算分**：健康分 + 完成度分 + 分类得分 + 最弱 3 类。
8. **存档与对比**：按下方存档约定写入档案，有历史则生成对比摘要（双分变化、新增修复、遗留问题）。

## 状态标记与评分（双分数）

**审查项状态**（填在状态列）：

| 标记 | 含义 | 分值 |
|---|---|---|
| ✅ 通过 | 该项已完善 | 1 |
| ⚠️ 待改进 | 已有基础但不够完善，或拿不出证据 | 0.5 |
| ❌ 缺失 | 完全没有 | 0 |
| ➖ 不适用 | 系统类型/阶段不涉及 | 不计入分母 |

**功能对照状态**：

| 标记 | 含义 |
|---|---|
| ✅ 已完成 | 功能按规划实现 **且验收标准达标**（有 feature-spec 时按 spec 的测试方法+正常结果核对；无 spec 时以代码/测试证据为准） |
| 🟡 部分完成 | 实现了一半或带明显缺口，**或实现了但验收标准不满足** |
| ❌ 未完成 | 规划了但没做 |
| 🚫 已取消 | 不再计划（不计入分母） |
| ⭐ 规划外新增 | 超出规划做的（不计完成度，单独标注——外包验收时是交付质量问题） |

**健康分** = 有效得分 ÷ 有效项数 × 100（➖ 不计）
**完成度** = (已完成 + 0.5 × 部分完成) ÷ (规划总数 − 已取消) × 100%

**等级映射**（健康分）：≥90 健康（绿）/ 75–89 良好 / 60–74 及格 / <60 待补强（红）

**分类得分**：14 类各自算（同类内等权），报告里按分排序，标出最弱 3 类。

## 报告输出格式（评估结束时呈现给用户）

```markdown
# 系统体检报告：<系统名>
日期：YYYY-MM-DD ｜ 版本：<模板名> ｜ 方式：自查 + 问答

## 双分数概览
- 🟢/🟡/🔴 **健康分：XX**（<等级>）
- **功能完成度：XX%**（<可评估/无法评估——缺规划基线>）

## 分类得分（按分排序，最弱 3 类标红）
## 功能完成度对照表
## 审查明细（填好的表）
## 待办优先级（❌ 先补，⚠️ 后优化）
## 与上次对比（如有历史档案）
```

## 存档约定（全局统一目录）

```
~/.claude/skill-records/system-audit/
  <system>/
    README.md                             # 档案索引：系统信息 + 历次双分曲线 + 待办清单
    audit-YYYY-MM-DD-<version>.md         # 本次完整体检报告
```

- 报告写盘后再给用户看，存档和展示同一份
- 更新 README.md：双分曲线加一个点（`| 2026-08-31 | core | 62 | 45% | 良好→待补强 |`），待办清单与本次报告对齐
- 对比摘要规则：与最近一次同版本评估对比双分；无历史则写「首次建档」

## 语言（v1.2 起，公开版）

- 首次运行：读 `~/.claude/skill-preferences.json` 的 `language` 字段
  - 存在 → 后续所有输出用该语言
  - 不存在 → **默认英文**，以英文询问用户常用语言（"Please tell me your preferred language (e.g. 'English', '中文', '日本語'): "），用户告知后写入该文件，本次起生效
- 语言影响：体检报告及所有生成内容（问答/提示/对比摘要）使用偏好语言；`templates/*.md` 是审查骨架，列名按偏好语言渲染
- 文件共享：`~/.claude/skill-preferences.json` 为全部 skill 共享，**问一次处处生效**
- 本仓库**不携带**该配置文件——每个安装者首次运行自行询问

## 红线

- 拿不出证据的项标 ⚠️「未找到」，**禁止凭感觉填 ✅**
- 规划基线缺失时完成度标「无法评估」，**禁止编造功能清单**
- 有 feature-spec 时，**验收标准不满足不得判 ✅**（双重判定）
- 只读操作自查，不修改被审系统的任何文件
- 涉及密钥/token 的内容只写「存在/不存在 + 存放位置类型」，严禁把值写进报告
